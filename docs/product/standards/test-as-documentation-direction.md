# 测试即文档重构方向

> 状态：重构进行中。本文记录最终目标；当前已经实施的规则以[测试即文档约定](./test-as-documentation.md)为准。

## 核心思想

测试即文档的目标不是把测试结果整理成更易读的规格或报告，而是直接产出一份完整的产品说明书。这份说明书面向产品用户、第三方和产品评审人员，不以软件作者为默认读者。

测试是说明书的执行和验证方式。每次测试成功都应证明：当前版本的软件仍然可以按照说明书记载的操作逻辑，完成对应的用户任务并产生承诺的用户可见结果。

因此，测试即文档首先是产品说明书，其次才是自动化测试。

## 单一事实来源

测试和文档不应各自维护一套内容，再依靠人工把两者同步。产品说明书中的用户任务、操作顺序、业务对象流转和可见结果，应当与可执行测试共享同一个产品语义来源。

文档由这份语义来源生成，测试也针对同一份语义来源执行。这样，文档描述的每个关键操作和结果都有可执行验证，测试通过后产生的文档也不会因为人工遗漏而偏离测试实际覆盖的流程。

这里的“完全吻合”指产品语义和用户可见行为吻合，不要求把每个 `expect`、内部状态或测试实现逐字呈现在文档中。测试可以包含文档不需要展示的技术断言，但不能验证一套用户逻辑、同时生成另一套用户说明。

产品说明书应当保留最近一次完整产品操作测试成功生成的版本。后续测试失败时，不能用失败结果覆盖这份已验证说明书；失败状态和差异应作为审查信息单独呈现。这样读者始终能区分“当前已验证的产品承诺”和“本次运行发现的偏差”。

## 要解决的问题

常规技术测试通常从模块、接口、状态、异常分支或历史缺陷出发。这样的测试适合内部开发，但容易产生以下局限：

- 单条测试为何存在，往往只有编写测试和维护模块的人清楚；
- 测试覆盖了许多局部细节，却没有锚定一个稳定、用户可见的产品功能；
- 不同模块的测试彼此独立，无法说明用户为何进入模块、前一步产生了什么，以及产物接下来如何使用；
- 测试通过只能说明若干实现行为没有回归，不能说明产品的完整操作逻辑仍然成立；
- 从这些测试生成的内容更接近验收规格、覆盖清单或证据报告，而不是可以独立阅读的产品说明书。

重构后的测试即文档需要补上这一层整体性。

## 产品说明书是第一产物

生成的正式文档应当脱离测试源码独立成立。不了解 Playwright、代码结构和内部存储的读者，也应能通过它理解和审查产品。

说明书需要回答：

- 产品帮助用户完成什么工作；
- 一项任务适用于谁，在什么情况下开始；
- 开始前需要准备哪些真实材料或产品对象；
- 用户按照什么顺序操作，每一步会看到什么反馈；
- 前一步产生的对象如何成为后一步的输入；
- 哪些选择会改变后续流程；
- 任务完成后产生什么，以及如何继续下一项工作；
- 用户可能实际遇到哪些中断或错误，以及如何恢复。

测试编号、执行状态、断言、夹具、内部数据结构、源码入口和覆盖数量可以作为附属证据，但不能构成说明书的叙事骨架。

## 以完整用户任务组织测试

产品操作测试的基本单位不是一个组件、接口或孤立行为，而是一项可以由用户说出的完整任务。测试从用户能够理解的起点开始，沿真实界面推进，直到产生有业务意义的最终结果。

以 LS101 的主线为例，系统性的产品操作测试应能够验证下面的对象链：

```text
评分单元 ──────────────┐
                       ├─> 试卷模板 ──生成──> 可运行试卷
题型定义 ──> 题组 ──────┘                         │
                                                  └─运行──> 作答包
                                                               │
                                                               └─导入──> 作答记录
                                                                            │
                                                                            └─评分──> 评分结果
                                                                                         │
                                                                                         └─结算──> 结算批次 / 报告
```

前一步产生的核心业务对象应被后一步真实使用。不能用测试夹具替代主线中的中间产物，再把彼此独立的模块测试拼接成一条看似完整的用户旅程。

除贯穿产品的标准主线外，还可以有面向真实用户任务的独立说明，例如重新生成试卷、导入已有作答、恢复中断流程或重新评分。它们仍需具备明确的用户目的、起点和最终产物。

## 产品操作测试与技术测试

两类测试服务不同目的，应当同时保留：

- 技术测试面向软件作者，验证组件、进程契约、持久化、异常边界、算法和历史回归；
- 产品操作测试面向用户和产品审查，验证完整任务、对象流转、用户决策和可见结果。

产品操作测试内部仍然可以使用断言、临时数据、服务替身和其他技术手段，但这些只是执行基础设施。它们不应决定说明书的章节结构，也不应以“本地记录”“原子写入”“测试夹具”或内部接口等措辞进入用户文档。

局部产品行为测试仍然有价值，但只能作为主线说明的补充证据或技术回归，不能代替完整产品功能的锚点。

## 稳定的产品审查依据

重构后的说明书同时承担产品审查基线。稳定性来自用户任务、产品对象、操作顺序和用户可见结果，而不是当前代码模块或测试实现。

评审人员应能直接依据说明书回答：

- 产品当前承诺支持哪些完整任务；
- 每项任务的标准操作逻辑是什么；
- 产品对象如何产生、流转和形成最终结果；
- 当前界面是否仍然实现了说明书描述的流程；
- 一次产品变更究竟改变了实现细节，还是改变了对用户的产品承诺。

当产品行为有意变化时，应先明确说明书中的产品承诺如何变化，再同步调整执行测试。测试运行通过后，生成的说明书才成为当前版本的有效审查依据。

## 判断是否达到目标

可以用下面的问题检查一次重构是否真正完成：

> 删除文档中的测试编号、执行术语、源码链接和内部实现信息后，它是否仍然是一份完整、连贯、可供用户操作并可供第三方审查的产品说明书？

如果答案是否定的，产物仍然是测试规格或测试报告，而不是这里所说的测试即文档。

## 当前进度

第一阶段已经建立产品说明步骤的单一事实来源：每一步只在说明定义中声明一次用户动作和可见结果，测试正文按稳定 key 执行，Reporter 校验全部步骤按照说明书顺序完成后才发布文档。

当前已经有两段不替换中间产物的纵向任务：从题型草稿产生稳定题型和题组，以及从可运行试卷产生作答包并把同一份作答导入作答记录。

从评分单元、题型和题组开始，经过模板制卷、考试运行，最终到评分结算的单一完整主线尚未贯通。现有制卷、生成和评分说明仍有独立前置状态，不能视为完整产品主线的替代品。
