# 机房服务端 API 设计

状态：待确认的 API 草案，尚未实现。

本文件细化[机房练习软件设计](./lab-deployment-design.md)中的跨端契约，不改变其中已经确认的功能边界。历史文档不作为接口要求来源。路径、字段及默认参数在本草案确认后再作为实现依据。

## 1. 范围与基本约定

服务仅随教师端安装，远程通信使用 HTTPS。API 根路径为 `/api/v1`，下文路径均相对于此根路径。

接口分为公开服务信息、教师管理、设备入网、学生业务四组。教师端与学生端主动请求服务端；首版使用心跳和轮询，不引入 WebSocket、广播发现或服务端主动连接学生机。

激活、启动参数、单实例、本机服务进程启停、安装升级及离线恢复不是远程 API。应用中的这些操作仍由桌面宿主和安装体系处理。

### 1.1 编码、身份与版本

- JSON 使用 UTF-8；时间为 UTC RFC 3339 字符串，字节数和计数为非负整数。
- 服务生成的资源 ID 使用 UUID；包内 `packageId` 保留原值，不要求它是 UUID，也不直接将其作为文件路径。
- 归档摘要使用 SHA-256，JSON 与自定义请求头中使用小写十六进制。
- `releaseVersion` 是学生端与服务端共用的精确发布版本标识，包含预发布标记；不以仅主版本相同作为兼容。
- 每个请求携带 `X-LS101-Client-Version`。角色由认证凭证决定，不能通过自报角色改变权限。
- 基础协议由 URL 中的 `v1` 标识。学生端版本不同但协议兼容时，只允许诊断连接；教师端按管理协议兼容性检查。
- 教师和学生令牌均使用 `Authorization: Bearer <token>`，不放入 URL。

成功响应直接返回对象，创建资源通常为 `201`，读取与更新为 `200`，无响应体的成功删除为 `204`，异步任务受理为 `202`。列表统一为：

```json
{
  "items": [],
  "nextCursor": null
}
```

列表默认每页 50 条，最多 200 条，使用不透明 `cursor`；服务端固定排序并使用 ID 作为同值排序补充。游标绑定筛选条件，不保证遍历期间资源完全静止。

### 1.2 错误

```json
{
  "error": {
    "code": "SERVICE_MAINTENANCE",
    "message": "服务处于维护模式，正式作答提交已暂停。",
    "requestId": "请求追踪编号",
    "details": { "mode": "maintenance", "modeRevision": 7 }
  }
}
```

客户端依赖 `code`，不解析 `message`。响应同时提供 `X-Request-Id`。错误响应不包含文件系统路径、密钥、令牌或完整作答。

| HTTP 状态 | 常见错误码 | 含义 |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | 参数、请求头或格式错误 |
| 401 | `AUTH_REQUIRED`、`TOKEN_EXPIRED`、`TOKEN_REVOKED` | 无有效凭证 |
| 403 | `DEVICE_DISABLED`、`LICENSE_INACTIVE`、`ENROLLMENT_REJECTED` | 无操作权限或许可无效 |
| 404 | `NOT_FOUND` | 资源不存在或不属于调用者 |
| 409 | `SERVICE_MAINTENANCE`、`VERSION_MISMATCH`、`REVISION_CONFLICT`、`CONTENT_CONFLICT`、`RESOURCE_BUSY` | 当前状态不允许或内容冲突 |
| 413 | `PAYLOAD_TOO_LARGE` | 请求或解压结果超限 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | 请求内容类型不支持 |
| 422 | `INVALID_EXAM`、`INVALID_SUBMISSION` | 包内容校验失败 |
| 429 | `RATE_LIMITED` | 超出频率或并发限制 |
| 503 | `SERVICE_NOT_READY`、`STORAGE_UNAVAILABLE` | 服务初始化、数据升级、备份写入屏障或存储异常 |

需要等待的响应可提供 `Retry-After`。网络超时、认证失败和维护拒绝均不表示作答未收取，客户端必须按交卷规则处理。

### 1.3 幂等与并发

有天然稳定 ID 的操作优先使用 `PUT`。创建入网批次、维护任务、清理计划、备份等 `POST` 请求必须携带随机 `Idempotency-Key`，客户端在发请求前持久化该键。

同一主体、路由和键对应同一逻辑操作：相同有效载荷返回原资源，不同有效载荷返回 `CONTENT_CONFLICT`。回放不得延长入网有效期、重新执行已取消任务或绕过当前授权；业务仍需检查当前身份及状态。

有限生命周期任务在其结果记录保留期间保留幂等映射。作答收卷去重不采用短时缓存，随持久收卷记录或删除标记保留。

教师对模式和可变配置使用 `expectedRevision` 防止多个教师窗口覆盖彼此修改。冲突返回当前版本，由 UI 刷新后重新决定。

## 2. 服务信息与鉴权

### 2.1 公开信息

`GET /info` 不要求应用令牌，只返回连接所需的最小信息：

```json
{
  "serverId": "服务 UUID",
  "name": "第一机房",
  "apiVersion": 1,
  "releaseVersion": "发布版本",
  "serverTime": "2026-09-05T08:00:00Z",
  "readiness": "ready"
}
```

`readiness` 为 `ready`、`initializing`、`upgrading`、`unavailable` 或 `license-inactive`。公开信息不包含设备、学生、试卷列表、管理凭证或内部路径。

HTTPS 对端公钥必须先通过客户端已有信任配置校验；不能从 `/info` 响应重新建立对当前连接的信任。

### 2.2 教师会话

| 方法与路径 | 请求 | 响应与规则 |
| --- | --- | --- |
| `POST /teacher/sessions` | 远程为 `{ "password": "..." }`；本机免密为 `{}` | 返回 `token`、`expiresAt`、`serverId` |
| `DELETE /teacher/sessions/current` | 无 | 撤销当前会话，返回 `204` |
| `GET /teacher/security` | 无 | 返回 `{ "revision": 1 }`，不返回密码或密码校验值 |
| `PUT /teacher/security/password` | `newPassword`、`expectedRevision` | 更改管理密码，返回更新后的 `{ "revision": 2 }`，撤销既有教师会话，要求重新登录 |

安全配置使用独立、持久化的 `revision`，初始为 1，与 `/teacher/settings` 的修订号互不通用。教师登录后通过 `GET /teacher/security` 取得修改密码所需的 `expectedRevision`。密码更新、修订号递增及既有教师会话撤销必须原子生效；版本冲突返回 `REVISION_CONFLICT`，在 `details.revision` 中提供当前安全配置版本，不修改密码或撤销会话。成功修改后，包括发起修改的会话在内，所有既有教师会话均失效。

会话默认有效 8 小时，过期重新认证，不建设用户账户或多级教师角色。服务许可无效时不能创建管理会话。

本机免密同时要求实际连接为回环来源，以及本机调用来源校验。会话入口只接受 JSON，不接受表单或查询参数密码；拒绝任意网页 Origin 和宽泛 CORS，不相信 `X-Forwarded-For`。具体 Electron 本机调用标识由宿主接口提供，不作为远程权限证明。

### 2.3 学生凭证

每台设备使用自己的长期凭证。教师禁用设备时保留诊断连接但禁止业务；重置绑定时撤销凭证，之后必须重新入网。凭证不因教师管理密码变化或入网文件过期而失效。

学生激活检查由应用执行，服务端同时校验自身许可、设备凭证、设备禁用状态、客户端版本及模式。首版不通过客户端自报 `activationState` 建立防篡改的远程许可证证明。

## 3. 入网批次与文件

### 3.1 教师接口

| 方法与路径 | 请求或用途 | 规则 |
| --- | --- | --- |
| `POST /teacher/enrollments` | `validForSeconds`，默认 600；`expectedModeRevision` | 自动进入维护，创建批次，返回批次及当前模式 |
| `GET /teacher/enrollments` | 列表 | 返回状态、有效期和注册数量，不返回入网秘密 |
| `GET /teacher/enrollments/{id}/file` | 下载签名入网文件 | 仅有效且未撤销批次可下载；不刷新有效期 |
| `DELETE /teacher/enrollments/{id}` | 关闭或撤销批次 | 幂等，保持维护模式，不影响已绑定设备 |

首版一个服务同时只开放一个入网批次。新建前需关闭旧批次；相同幂等键的重试返回原批次。有效期按服务端签发时间计算，不能由学生机时钟延长。

创建批次和进入维护必须构成一个一致的状态变更，不能出现正常模式仍接受新注册。过期与撤销检查在注册提交时再次执行。

### 3.2 文件格式

建议 `.lsjoin` 文件使用标准 JWS 紧凑序列化，固定 `ES256` 算法，公钥为 P-256；TLS 证书与入网签名对应同一服务身份公钥。指纹为该公钥 DER SPKI 的 SHA-256，展示和配置采用 `sha256:<hex>`。

JWS 头只接受固定 `alg`、用途 `typ` 和公钥标识 `kid`，拒绝 `none`、算法降级及远程取钥地址。有效载荷包含：

```json
{
  "formatVersion": 1,
  "purpose": "ls101-device-enrollment",
  "serverId": "服务 UUID",
  "baseUrl": "https://192.168.1.10:8443/",
  "publicKeyFingerprint": "sha256:公钥摘要",
  "enrollmentId": "批次 UUID",
  "issuedAt": "2026-09-05T08:00:00Z",
  "expiresAt": "2026-09-05T08:10:00Z",
  "enrollmentSecret": "随机短期秘密"
}
```

客户端使用受控部署参数或既有绑定中的可信指纹，校验 TLS 公钥及文件签名。文件中自报的指纹不能成为首次信任依据。服务端验证自己的签名、用途、服务身份、批次状态和秘密。

文件是可在短期内供多台设备使用的持有者凭据；签名阻止伪造与篡改，不阻止持有真实文件的设备申请注册。文件及秘密不得出现在日志中。

### 3.3 注册与重复调用

`PUT /enrollment/devices/{installationId}` 提交：

```json
{
  "enrollmentFile": "完整 JWS 字符串",
  "deviceSecret": "客户端生成并预先持久化的 256 位随机秘密",
  "computerName": "LAB-PC-023",
  "platform": "win32",
  "releaseVersion": "发布版本"
}
```

`installationId` 是首次部署时本机生成并持久化的 UUID，`deviceSecret` 使用不带填充的 Base64url 编码，同样先落盘再请求。服务端批准注册后返回 `deviceId`、`deviceNumber`、`registeredAt` 和当前维护状态。设备 Bearer 凭证格式为 `d.<deviceId>.<deviceSecret>`；服务端仅保存秘密的安全校验值，前缀不能替代真正的凭证验证。

这种方式避免注册响应丢失后无法取回服务端一次性生成的秘密：同一安装 ID 和相同秘密可重复请求，返回同一设备。安装 ID 相同但秘密不同不能接管既有设备，返回冲突；管理员重置绑定后才允许重新注册。

重复请求仍需有效入网文件；文件已过期则重新取得批次文件，使用本机已有安装 ID 和秘密重试，不生成重复设备。已持有有效设备凭证的普通重连不再调用注册接口。

注册要求许可有效、版本完全一致、服务处于维护且批次开放。软件忙碌和未激活的启动命令在学生端提前拒绝，不能通过注册接口改变其单实例处理规则。

## 4. 模式、连接与心跳

### 4.1 教师切换模式

| 方法与路径 | 用途 |
| --- | --- |
| `GET /teacher/service` | 服务模式、修订号、版本、健康状态、开放入网批次、活动任务和设备汇总 |
| `PUT /teacher/service/mode` | `{ "mode": "maintenance", "expectedRevision": 6 }` |

模式只有 `normal` 和 `maintenance`，默认维护。切换成功返回当前模式和递增的 `modeRevision`。

进入维护与正式收卷提交共用一致的状态判断：维护切换成功后，不再允许新的正式作答持久化提交。尚未提交完成的在途请求中止，返回 `SERVICE_MAINTENANCE`；切换前已经持久化的结果保留，不回滚。

退出维护前必须关闭入网批次，并结束或取消测试和清理执行；仍有有效执行租约则返回 `RESOURCE_BUSY`。离线设备的任务租约过期并停止执行后才能解除这一限制。教师明确切换正常，文件过期、测试结束或管理 UI 退出都不自动切换。

### 4.2 学生连接状态

`GET /student/state` 在首次连接、重连及需要重新核对时调用，返回：

```json
{
  "serverId": "服务 UUID",
  "serverTime": "2026-09-05T08:00:00Z",
  "releaseVersion": "发布版本",
  "mode": "maintenance",
  "modeRevision": 7,
  "device": {
    "id": "设备 UUID",
    "number": "023",
    "room": "第一机房",
    "seat": "第 3 排 2 号",
    "displayName": "靠窗座位",
    "enabled": true,
    "revision": 4
  },
  "availability": "maintenance",
  "allowedOperations": ["heartbeat", "maintenance-task"],
  "heartbeatIntervalSeconds": 5,
  "offlineAfterSeconds": 20
}
```

`availability` 为 `ready`、`maintenance`、`version-mismatch`、`disabled`、`license-inactive` 或 `service-unavailable`。返回状态便于 UI 展示，所有业务接口仍需独立执行同样检查。

`device` 是教师配置的完整设备信息，`room`、`seat`、`displayName` 未设置时为 `null`；`revision` 是第 4.4 节的设备配置修订号。每次状态查询和心跳响应均返回最新完整 `device`，学生端据此更新维护画面，无需重新入网。并发状态查询与心跳响应乱序时，同一绑定下较小的设备修订号不得覆盖较大的修订号；切换绑定时清除旧设备配置缓存。

凭证有效但版本不一致的设备可以读取最小状态、发送诊断心跳，不领取任务、浏览试卷、交卷或查询回执。已撤销凭证则返回 `401`，不提供设备信息。

### 4.3 心跳

`POST /student/heartbeat` 发送本机状态，响应沿用 `/student/state` 的字段，包含完整最新 `device`，并增加 `heartbeatAccepted` 和 `taskIds`。`heartbeatAccepted` 表示本次快照是否被采纳，`taskIds` 为可领取任务的 ID 数组，不直接执行任务。

```json
{
  "runtimeId": "本次应用运行 UUID",
  "runtimeGeneration": 3,
  "sequence": 12,
  "activationState": "active",
  "phase": "maintenance-idle",
  "currentPractice": null,
  "submissionSummary": {
    "waitingFirstUpload": 2,
    "unconfirmed": 1,
    "failed": 1
  },
  "lastError": null
}
```

`phase` 包含 `idle`、`preparing`、`practicing`、`saving`、`maintenance-idle`、`testing` 和 `error`。上传是并行任务，用统计反映，不将单次后台上传误当作无法继续练习的前台阶段。

`currentPractice` 在相关阶段包含 `submissionId`、`examId`、学生姓名学号和当前页面或步骤；它是状态报告，不替代最终作答包或成功回执。

统计是本机全部记录的快照，包括换绑前遗留记录。`unconfirmed` 可以与 `failed` 重叠，不能直接相加为总数。服务端以统计接收时间作为 `submissionSummaryUpdatedAt`，离线保留最后已知值，未上报为 `null`，不填零。

`runtimeGeneration` 是按当前设备凭证绑定持久化的运行代次，`runtimeId` 是本次应用运行生成的随机 UUID。首次使用新凭证从代次 1 开始；每次应用重启，必须先原子递增并可靠保存代次，再发送本次运行的首条心跳。普通断线重连不更换代次或运行 ID；同一次运行的 `sequence` 从 1 开始递增，学生端串行发送心跳。代次和序号均为不超过 `9007199254740991` 的正整数，不允许回绕。

服务端按当前设备凭证绑定持久化已接受的最大代次、对应运行 ID 和最大序号，并与心跳快照及接收时间原子更新。通过凭证与诊断准入校验后，按以下规则处理：

- 尚无记录，或代次更大：接受快照，将该代次及运行 ID 设为当前运行，以本次序号建立新的运行内顺序。
- 代次相同且运行 ID 相同：仅接受比已保存序号更大的快照。
- 代次更小，或同一运行的序号小于等于已保存序号：返回 `200`、`heartbeatAccepted: false` 和空 `taskIds`，不更新快照、在线时间或统计更新时间；仍返回最新连接状态与设备配置。
- 代次相同但运行 ID 不同：返回 `CONTENT_CONFLICT`，不改变当前运行或快照。

接受快照时返回 `heartbeatAccepted: true`，任务 ID 仍须按当前模式、版本和权限筛选。即使旧实例的首条心跳从未到达，只要新代次已被接受，旧代次的迟到请求就不能覆盖状态；服务端普通重启也不能丢失上述排序记录。学生端代次数据缺失、损坏或耗尽时不得沿用旧凭证将代次重置为 1，须报告本地状态异常，由教师重置绑定并重新入网；服务端仅在旧凭证撤销后为新凭证建立独立排序记录。

基础版本不匹配时只接收诊断字段，仍执行上述排序检查，不依据其心跳执行业务或维护任务。激活失效的学生端停止业务连接，服务端展示最后已知值及时间。

### 4.4 教师设备管理

| 方法与路径 | 请求或用途 |
| --- | --- |
| `GET /teacher/devices` | 按机房、在线状态、版本异常、关键字筛选 |
| `GET /teacher/devices/{id}` | 设备详情、最后心跳、练习状态、作答统计和任务状态 |
| `PATCH /teacher/devices/{id}` | 修改 `number`、`room`、`seat`、`displayName`、`enabled`，携带 `expectedRevision`；返回更新后的完整设备信息 |
| `POST /teacher/devices/{id}/reset-binding` | 撤销凭证及待执行任务；必须确认，使用幂等键 |

设备 `id` 是不可变身份主键，计算机名不作为唯一键。`number` 对应注册响应中的 `deviceNumber`，由服务端初次分配，之后只有教师明确修改才改变。编号为保留前导零的字符串，去除首尾空白后不得为空，在同一服务的全部设备记录中唯一（包括禁用设备，按大小写敏感的完整字符串比较）。编号占用返回 `CONTENT_CONFLICT`，不应用同一请求中的其他修改；修改编号不改变设备 ID、凭证、既有作答或任务归属。

设备列表中的每项、设备详情和修改成功响应均包含第 4.2 节完整 `device` 对象的字段。设备配置 `revision` 初始为 1，教师实际修改任一可变字段时原子递增；心跳和在线状态更新不改变此修订号。`expectedRevision` 使用该值，冲突时返回 `REVISION_CONFLICT` 和 `details.revision`，由教师重新读取设备详情后决定。PATCH 中省略字段表示不修改，`room`、`seat`、`displayName` 可用 `null` 清除。学生端通过后续状态查询或心跳取得变更后的配置。

禁用不强制丢弃进行中的本地作答，但阻止后续远程业务；重新启用后按原提交状态继续。

重置绑定保留服务端作答和必要的设备归属记录。后续重新入网不能将其他安装 ID 的记录转移过来。学生端更换当前绑定后，不再领取旧服务任务；旧服务待确认作答仅按功能设计保留回执核对或导出路径。

## 5. 试卷接口

### 5.1 教师试卷管理

| 方法与路径 | 用途 |
| --- | --- |
| `GET /teacher/exams` | 全部试卷列表，按关键字和上架状态筛选 |
| `POST /teacher/exams` | 上传原始 `.lsexam` 二进制 |
| `GET /teacher/exams/{examId}` | 获取元数据 |
| `GET /teacher/exams/{examId}/archive` | 下载完整原归档 |
| `PATCH /teacher/exams/{examId}` | 仅修改 `published`，携带 `expectedRevision` |
| `DELETE /teacher/exams/{examId}` | 删除试卷，不删除作答 |

上传内容类型为 `application/x-ls101-exam`，使用 `X-LS101-Archive-SHA256` 声明摘要，服务端自行计算并核对。服务端流式接收至临时文件，完成包校验后才发布记录。

返回元数据包含 `examId`、包内 `packageId`、`title`、`archiveSha256`、`archiveBytes`、`pageCount`、`resourceCount`、`published`、`importedAt` 和 `revision`。

同包 ID 同摘要返回已有记录及 `duplicate: true`，不同内容返回 `CONTENT_CONFLICT`。首次上传成功默认上架。服务端不信任上传文件名决定存储路径。

### 5.2 学生下载与缓存

| 方法与路径 | 用途 |
| --- | --- |
| `GET /student/exams` | 正常模式下列出已上架试卷 |
| `GET /student/exams/{examId}/archive` | 正常模式下下载已上架试卷 |

列表提供学生缓存所需元数据，不包含教师管理配置。下载返回 `Content-Length`、固定归档摘要和安全的 `Content-Disposition`。首版完整文件下载，失败重新下载，不建设分片上传或断点传输协议。

学生端下载完成后再次校验摘要和包内容，通过本地协议播放，不把服务端 URL 直接交给播放器。服务进入维护时不再准入新的正式下载；已开始下载可完成缓存，但不能据此开始练习。

不为未来浏览器播放器额外开放匿名静态目录。将来需要远程播放时，再在现有包格式契约上增加有明确权限的资源访问方式。

## 6. 练习开始许可

建议用同一个固定 UUID 作为本次练习标识和最终 `submissionId`。学生端在申请开始前生成并持久化，播放器通过通用宿主参数使用该编号，不在保存重试时重新生成。

`PUT /student/practices/{submissionId}` 请求：

```json
{
  "examId": "服务端试卷 UUID",
  "archiveSha256": "本地已验证归档摘要",
  "candidate": { "candidateId": "学生学号", "displayName": "学生姓名" }
}
```

服务端检查正常模式、相同版本、设备启用、试卷上架和摘要一致后，持久化本次准入，返回 `submissionId`、`grantedAt`、`startBefore` 和 `modeRevision`。首版开始期限建议 30 秒。

请求放在播放器预检和麦克风检查完成之后，正式时间线开始之前。客户端收到有效许可后立即开始；已获知更新的维护状态则不开始。许可签发与模式切换在服务端有明确先后，不能要求网络上的所有客户端瞬时同步。

响应丢失可使用相同 ID 和相同内容重试，但必须重新检查当前准入状态；不得因幂等而在维护或禁用后重新授予开始许可。有效期内的重复请求返回原许可，不延长开始期限；开始期限已过且本机尚未开始时，使用新的作答 ID 重新申请，原编号不重复用于另一次练习。服务端不将心跳当作可信的防作弊开始证明。

开始期限只限制开始时间，不作为作答上传截止时间。已经获得准入的作答可在练习结束、网络恢复或版本升级后提交；服务端保留必要准入信息，试卷删除不级联删除它。

服务端将准入的设备、试卷包身份、摘要和学生信息与最终作答关联，拒绝一个编号对应不同练习内容。此机制服务于数据归属与重试，不建设正式考试控制系统。

## 7. 正式交卷与回执

### 7.1 上传

`PUT /student/submissions/{submissionId}` 上传完整 `.lssubmission` 二进制：

```text
Content-Type: application/x-ls101-submission
X-LS101-Archive-SHA256: <原归档 SHA-256>
Authorization: Bearer <本设备凭证>
X-LS101-Client-Version: <当前发布版本>
```

服务端依次检查当前模式与权限、作答编号归属、上传大小、实际摘要、包结构、资源及与开始许可的对应关系。包内 `submissionId` 必须等于路径值，不能覆盖其他设备记录。

校验与持久化成功返回 `201` 和成功回执；相同编号、相同摘要的重复请求返回 `200` 和同一回执，不能产生第二条作答。相同编号不同摘要返回 `CONTENT_CONFLICT`。

同一编号正在接收时，重复上传返回 `RESOURCE_BUSY`，客户端先核对结果，不同时发出多份归档。上传采用临时文件、内容校验和持久提交，半包或未完成的索引不可见为成功作答。

服务端在最终持久化提交前再次校验模式，与维护切换按同一个一致性边界排序。不得只在开始接收请求时检查一次模式，否则大文件会在进入维护后继续被正式收取。

### 7.2 回执查询

`GET /student/submissions/{submissionId}/receipt` 用于查询归属本设备、尚待客户端确认的逻辑提交。接口以当前设备权限和原准入或收卷归属检查，不开放全校作答查询。服务端无法获知回执是否已在学生机落盘，因此不增加确认回执的第二次握手；客户端负责停止查询已归入历史的记录。

成功返回 `200`，按 `status` 区分：

| `status` | 含义 | 客户端处理 |
| --- | --- | --- |
| `not-received` | 已核实该编号归本设备，当前没有已提交记录或在途接收 | 按任务来源决定首次发送、维护恢复自动重发或手动重试 |
| `receiving` | 同一编号尚在接收或提交 | 保留待核对，按 `retryAfterSeconds` 查询 |
| `received` | 已可靠收取，文件仍在服务端 | 持久化回执，归入历史 |
| `deleted` | 曾成功收取，后来由教师删除 | 持久化原回执及删除状态，归入历史，不重传 |

成功回执形状如下，`deleted` 状态额外包含 `deletedAt`：

```json
{
  "status": "received",
  "receipt": {
    "receiptId": "回执 UUID",
    "serverId": "服务 UUID",
    "deviceId": "设备 UUID",
    "submissionId": "固定作答 UUID",
    "archiveSha256": "原归档摘要",
    "receivedAt": "2026-09-05T08:30:00Z"
  }
}
```

上传成功响应使用相同形状。回执中的身份、编号和摘要必须与本地任务匹配，不能仅凭 HTTP `200` 判断提交成功。

未知编号或不属于本设备的编号返回 `NOT_FOUND`，不能把这个错误等同于 `not-received`。恢复旧备份导致准入信息缺失时，不自动重建权限或补齐作答，按既定边界人工导出处理。

服务端重启后，恢复过程处理残留临时接收状态，完成一致性检查才提供回执查询；不能永久留下 `receiving`，也不能在持久化结果未知时回答 `not-received`。

### 7.3 维护与失败处理

维护期间，正式上传和回执查询均返回 `SERVICE_MAINTENANCE`，连已经存在的正式回执也不通过学生接口查询。维护前成功提交的在途响应可能晚到，学生仍可保存其中的有效回执；这是本地完成确认，不是维护期间新发起查询。

恢复正常且准入条件满足后：

- 尚未发送的任务自动开始首次上传。
- 因维护中止的任务先查回执；`not-received` 时自动重发原归档，`received` 或 `deleted` 时归入历史。
- 维护前已经失败的任务允许自动核对回执，但确认未收取以后仍由学生手动触发重试。
- 查询超时、认证失败、维护或服务异常时保留结果未确认状态，不推断未收取。
- 自动重发发生普通上传失败后进入异常列表，不无限自动重试，不阻塞符合条件的新练习。

服务明确返回维护拒绝或客户端因收到维护状态主动取消时，记录维护暂停原因；普通网络错误不因之后恰好发现维护而追溯改写为可自动重传的任务。

客户端一旦持久化成功回执，逻辑提交结束。之后不轮询历史回执，不核对两端库存，不因服务端删除或恢复旧备份而重新上传。

### 7.4 教师作答管理

| 方法与路径 | 用途 |
| --- | --- |
| `GET /teacher/submissions` | 按试卷、学生、机房、设备和接收时间筛选 |
| `GET /teacher/submissions/{id}` | 归档元数据、来源设备、接收时间及摘要 |
| `GET /teacher/submissions/{id}/archive` | 下载原始 `.lssubmission` |
| `POST /teacher/submissions/export` | `{ "submissionIds": [...] }`，返回外层 ZIP，内部保留原作答包 |
| `DELETE /teacher/submissions/{id}` | 删除原归档，保留最小回执、摘要、归属和删除时间 |
| `POST /teacher/submissions/delete` | 显式 ID 列表及幂等键，批量删除 |

单次批量操作最多 500 个 ID，不能用实时筛选条件直接表示删除范围。批量删除返回逐项结果，UI 明确成功、已删除及失败项，不假装跨多个文件删除天然全有或全无。

批量导出在开始发送前检查全部目标，缺失目标明确失败；流式传输中断不产生可宣称完整成功的 ZIP。文件名包含稳定作答 ID，避免同名学生覆盖。导出不修改作答状态。

维护禁止的是学生正式收卷接口，教师对已经收到的作答仍可浏览、下载和删除。备份一致性屏障期间，冲突写入返回 `SERVICE_NOT_READY`。

## 9. 维护任务执行协议

### 9.1 固定任务类型

首版只接受 `deployment-test` 和 `history-cleanup` 两类任务。任务参数由服务端验证，不能包含可执行代码、命令行或任意文件路径。

教师创建的批次固定目标设备 ID，不在之后自动把新入网设备加入。每台设备有独立任务 ID、状态和结果，避免一台失败影响整个机房的记录。

任务状态为 `pending`、`running`、`cancel-requested`、`succeeded`、`failed`、`cancelled` 或 `expired`。在线与离线是设备状态，不能把离线任务算作成功。

### 9.2 学生领取与回报

| 方法与路径 | 请求或用途 |
| --- | --- |
| `GET /student/tasks` | 返回本设备在当前模式和版本下可领取的任务 |
| `POST /student/tasks/{id}/claim` | `runtimeId`，领取并取得 `leaseId`、`leaseExpiresAt`、任务参数 |
| `PUT /student/tasks/{id}/lease` | `leaseId`、`runtimeId`，续租并取得取消状态 |
| `PUT /student/tasks/{id}/result` | 提交固定结果，包含 `leaseId`、状态、各项结果及错误 |

领取和续租必须维护、版本一致、设备启用。学生端本机也检查空闲且未在录音、保存归档或执行另一个维护任务。同一设备只允许一个正在执行的维护任务。

执行租约建议 30 秒，每 5 秒续租，不能超过任务最终有效期。客户端依据服务端时间及本地单调计时维护保守的剩余期限，失联不无限执行；续租失败、取消或租约到期时停止测试和新的清理操作，释放设备资源。

教师取消运行任务时置为 `cancel-requested`，等待设备确认停止或租约到期。服务端不把请求取消成功立即等同于真机已经停止。清理是逐文件操作，已经完成的删除无法回滚，结果记录实际完成数量。

领取响应丢失后，同一运行实例重复领取可取得同一有效租约，不重启任务。应用重启时先恢复本地任务执行日志；结果已完成则补报，不重新执行。旧租约不能启动新工作。

最终结果按任务和租约幂等保存，相同内容可重复回报，不同内容不能覆盖既有结果。已到期或已取消任务可以补收原执行者的迟到报告，单独标记 `late`，不能把任务重新变为可执行或覆盖取消、到期事实。

维护结束后可补报先前已经产生的结果，但不能领取、续租或执行新维护工作。这是结果记录接口，不是允许正常模式运行测试的入口。

## 10. 部署测试 API

### 10.1 教师接口

| 方法与路径 | 请求或用途 |

| `GET /teacher/test-suites` | 列出安装包内支持的套件、版本和测试项 |
| `POST /teacher/test-runs` | `suiteId`、`caseIds`、`deviceIds`、`expiresAt`；创建测试批次 |
| `GET /teacher/test-runs` | 测试批次列表 |

| `PUT /teacher/test-runs/{id}/devices/{deviceId}/confirmation` | 教师记录声音等人工核对结果，携带 `expectedRevision` |

| 方法与路径 | 用途 |
| --- | --- |
| `GET /student/tasks/{taskId}/test/exam` | 下载该任务指定的内置测试考试包 |
| `PUT /student/tasks/{taskId}/test/submission` | 上传本次测试产生的归档 |
| `GET /student/tasks/{taskId}/test/receipt` | 查询该测试提交结果 |

这些接口要求有效设备凭证、该设备拥有的测试任务、有效执行租约及维护模式。请求携带 `X-LS101-Task-Lease`，任务上下文固定测试包、测试作答 ID 和大小限制。

测试提交复用正式归档校验、摘要、持久化和幂等核心逻辑，但使用独立授权入口、测试存储和回执命名空间，不要求正常模式的正式开始许可。不能通过添加 `test=true` 绕过正式接口限制。

重复提交及模拟回执丢失在任务自己的测试空间验证。模拟上传失败由内置执行器在受限场景完成，不关闭整机网卡或影响其他设备。

任务结束后不再允许测试文件上传，迟到的报告仍通过任务结果接口补报。测试录音和归档按测试保留策略清理，不进入正式作答、异常列表或学生历史。

报告不得把设备调用成功等同于音频实际可听。录音、播放、显示等自动结果和管理员现场确认分别呈现。

## 11. 学生历史清理 API

### 11.1 创建、预览与确认

| 方法与路径 | 请求或用途 |
| --- | --- |
| `POST /teacher/history-cleanups` | `deviceIds`、`submittedBefore`、`expiresAt`；创建待确认清理计划 |
| `GET /teacher/history-cleanups` | 清理计划列表 |
| `GET /teacher/history-cleanups/{id}` | 各设备预览数量、字节数、执行状态和错误 |
| `POST /teacher/history-cleanups/{id}/confirm` | `expectedRevision`、选中的设备及各自 `selectionDigest` |
| `POST /teacher/history-cleanups/{id}/cancel` | 取消未执行部分，运行部分按任务协议停止 |

计划创建只触发只读预览，不删除文件。预览与执行均使用 `history-cleanup` 任务，参数中的 `phase` 分别为 `preview` 和 `execute`。

设备预览时筛选本机全部已提交历史，包括换绑前历史；依据完整作答中的提交时间早于固定 `submittedBefore` 且本地持有成功回执的条件，生成本地持久化的候选快照，回报数量、字节数和 `selectionDigest`。

教师确认固定设备的候选快照，执行任务引用该摘要。未完成预览的离线设备不能伪造预览数量或自动纳入已确认范围，可等待上线或明确排除后确认。预览完成后离线的设备，仍可在计划有效期内上线领取已确认任务。

### 11.2 执行约束

执行时必须仍绑定签发任务的当前服务、处于维护空闲、租约有效且快照摘要匹配。再次校验每条记录已有成功回执，只删除确认快照内的文件，不把后来新增历史纳入，也不删除异常或处理中归档。

快照丢失或不匹配时报告失败，重新预览确认，不根据同一日期条件临时扩大删除范围。逐条持久化执行进度，重启后不会再次删除新文件或重复累计成功数量。

结果包含 `selectedCount`、`deletedCount`、`alreadyAbsentCount`、`skippedCount`、`failedCount`、实际字节数及错误。全部清理范围完成才标记成功，部分失败明确报告，教师可对剩余范围另建计划。

清理不查询原服务是否仍保存作答，不承担恢复旧备份的协调责任。学生端保留最小已提交标记，服务端保留自己的收卷去重记录。

更换绑定后不再执行旧服务的清理计划；新绑定服务可以按同样流程管理本机全部已提交历史。授权不来自历史的原服务归属，而来自本机当前绑定及本次明确确认。

## 12. 设置、日志与备份

### 12.1 服务设置

| 方法与路径 | 用途 |
| --- | --- |
| `GET /teacher/settings` | 服务名称、对外连接地址、容量和传输限制及修订号 |
| `PATCH /teacher/settings` | 修改可热更新配置，携带 `expectedRevision` |
| `GET /teacher/logs` | 按时间、级别和请求 ID 分页读取脱敏运行日志 |

此处设置修订号只用于 `PATCH /teacher/settings`，不覆盖管理密码；密码使用第 2.2 节独立的安全配置修订号。

监听地址、端口、数据目录、开机启动和进程启停放在教师端本机管理能力中，不在远程设置接口悄悄执行进程重启。对外连接地址用于签发新的入网文件，修改不会重新生成服务身份或自动让已有客户端改地址。

服务公开其有效传输限制，已认证的 `/student/state` 返回对应 `limits`：`maxExamArchiveBytes`、`maxSubmissionArchiveBytes`、`maxUncompressedBytes`、`maxArchiveFiles`。建议首版压缩归档最大 256 MiB，解压总量最大 512 MiB，文件数最大 10000；这些是待确认的初始参数。

JSON 控制请求单独限制为 1 MiB，入网文件单独限制为 64 KiB，不能套用归档的大体积上限。客户端发送前检查有效限制，服务端仍独立检查压缩大小、实际解压规模及安全路径。

日志不返回激活码、密码、令牌、入网文件内容或作答正文。用于维护的请求 ID 和设备 ID 可保留，不提供任意日志文件路径读取功能。

### 12.2 备份

| 方法与路径 | 请求或用途 |
| --- | --- |
| `POST /teacher/backups` | `encryptionPassword` 和幂等键，创建加密的一致性备份，返回 `202` 与备份 ID |
| `GET /teacher/backups` | 备份时间、版本、状态和大小列表 |
| `GET /teacher/backups/{id}` | 查询 `pending`、`running`、`ready` 或 `failed` |
| `GET /teacher/backups/{id}/archive` | 仅完成后下载加密备份 |

创建备份只允许维护模式且没有正在执行的测试、清理或其他冲突写入。快照期间建立写入屏障，相关变更返回 `SERVICE_NOT_READY`，快照完成后释放屏障并保持维护模式。

备份覆盖业务数据、配置、身份密钥、设备凭证校验信息、准入记录及收卷回执。使用标准加密归档实现，不设计自定义加密算法；密码不写日志或长期保存。处理幂等键时也不能将原密码写入通用请求重放记录。

恢复操作通过服务机本地管理流程在服务停止或隔离状态进行，不提供会覆盖正在运行服务的远程恢复接口。恢复旧快照的边界沿用功能设计，不自动要求学生补齐历史。

## 13. 持久化与清理边界

API 不规定数据库产品，但实现必须持久化以下业务事实：服务身份与模式、管理密码安全配置及其修订号、有效入网批次、设备凭证及设备配置修订号、设备编号和机房座位等配置、禁用状态、按设备凭证绑定隔离的心跳最大运行代次与运行 ID 及序号、试卷索引与归档、练习准入、成功作答与回执、删除去重标记、维护任务及其执行结果。

设备在线状态和当前阶段来自心跳，是有时间戳的观测结果。它们不能替代作答收卷事实，也不能因为教师 UI 刷新而变成业务完成记录。

正式归档、索引和回执需要可恢复的一致提交机制。应用进程崩溃后，接口要么返回完整收卷结果，要么明确未收取；恢复未完成时返回服务未就绪，不能对外暴露半完成状态。

删除试卷保留与既有练习准入和作答有关的必要元数据。删除服务端作答保留去重标记。删除学生历史不改变服务端归档和客户端已经成功提交这一事实。

有限维护任务、测试临时数据和过期入网秘密可以按明确策略回收。回收不能删除尚待恢复的正式提交事实，也不把历史清理变成作答重新上传的触发器。

## 14. 关键验收场景

本节描述后续实现需要验证的跨端契约，不表示已有 API 或测试通过。

1. 首次信任：未知指纹、篡改文件、错误签名、过期或撤销批次不能注册；相同安装 ID 和秘密重试不产生重复设备。
2. 角色隔离：学生不能获取教师接口、其他设备回执或任务；本机免密入口不能被普通网页跨源调用。
3. 精确版本：学生版本不同只能诊断，试卷、正式提交、回执查询和维护执行全部拒绝。
4. 模式竞争：上传已开始但尚未提交时切入维护，正式提交不落地；切换前已成功提交的回执仍能在恢复后查询。
5. 维护恢复：未首次发送任务恢复发送，维护中止任务核对后按结果重发或归档，已有失败任务不被重置为自动重试。
6. 幂等收卷：响应丢失、重复请求和进程重启均不重复收卷；同编号不同内容冲突；教师删除后不因迟到重试恢复文件。
7. 统计可见：维护期间新完成作答计入等待首次提交，未确认与异常分别显示，离线和未上报不显示为零。
8. 任务约束：只有当前绑定、合法类型、有效租约和维护空闲设备能执行；取消与过期能够停止执行，迟到结果不能重新激活任务。
9. 测试隔离：维护中测试上传可运行，但正式上传和正式回执查询仍拒绝；测试结果不进入学生正式历史。
10. 清理范围：仅清理教师确认快照内的已提交历史，异常和处理中记录保留；换绑取消旧服务执行资格，新教师可管理全部本机历史。
11. 升级与恢复：数据升级失败时业务 API 不可用且数据保留；恢复旧备份不触发已完成历史的重新上传或两端核对。
12. 心跳排序：旧实例首条心跳晚于新实例到达时被忽略，同一运行重复或乱序心跳不覆盖快照或刷新在线时间；服务端重启后仍拒绝旧代次，同代次不同运行 ID 返回冲突，客户端重启先持久化递增代次。
13. 设备配置：教师可修改编号、机房、座位和显示名；学生在下次心跳或状态查询后更新维护画面，迟到的旧修订号响应不能回退配置。重复编号或修订号冲突不产生部分更新，改号不改变设备身份和既有数据归属。
14. 密码版本：教师登录后可读取安全配置修订号并首次修改密码；设置修订号与安全修订号独立变化，旧安全修订号不能覆盖新密码，成功修改同时递增修订号并撤销全部既有教师会话。

## 15. 下一步设计顺序

先确认本草案的资源划分、维护边界和关键请求响应，再据此整理可机器校验的 OpenAPI 契约及共享类型。随后设计服务端持久化与事务边界、学生端状态机和教师端页面流程，最后分阶段实现。
