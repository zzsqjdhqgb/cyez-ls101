# 机房学生端状态与本地提交设计

状态：待审核，尚未实现。依据[功能设计](./lab-deployment-design.md)及 [API 契约](./lab-server-api-design.md)，宿主边界见[桌面设计](./lab-desktop-design.md)。

## 1. 状态的三个维度

renderer 中的应用控制器组织准入、练习与后台提交；main 提供持久化及网络能力。状态变更以事件和纯转换函数表达，副作用完成后再次派发结果事件，不由页面各自启动心跳或上传循环。

| 维度     | 状态                                                                                                                                                          | 生命周期                                           |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 准入     | `activation-required`、`local-unavailable`、`unbound`、`connecting`、`offline`、`version-mismatch`、`service-unavailable`、`disabled`、`maintenance`、`ready` | 一个应用实例一份；原始事实与推导页面分开保存       |
| 前台     | `idle`、`preparing`、`practicing`、`saving`、`testing`、`error`                                                                                               | 同一时刻至多一个练习或维护执行；后台上传不占此状态 |
| 单条提交 | `queued`、`sending`、`checking`、`retry-required`、`completed`、`manual-resolution`                                                                           | 每份完整作答独立持久化，多个记录可并行处理         |

激活、本地存储、绑定信任、版本、设备权限、模式按功能设计的顺序判断。`offline` 不抹掉最后已知维护锁或版本不一致事实；状态响应不能替代服务端业务鉴权。网络恢复后先读取状态再调度业务，不能仅凭 socket 连通恢复上传。

准入失效不会让已落盘文件消失。正在播放时普通断网、维护或设备禁用允许完成本地作答；停止新练习和新的远程操作。激活失效或已知版本不一致依功能设计停止业务，未完成时间线不承诺恢复；已形成的完整归档保持原状。

## 2. 页面和操作矩阵

| 条件                               | 前台显示                         | 本地查看/导出              | 新练习与正式上传                 |
| ---------------------------------- | -------------------------------- | -------------------------- | -------------------------------- |
| 未激活                             | 激活页                           | 禁止                       | 禁止                             |
| 本地数据初始化失败                 | 存储异常                         | 禁止应用内操作，保留原数据 | 禁止                             |
| 未绑定且已激活                     | 等待入网                         | 首版不开放                 | 禁止                             |
| 版本不一致                         | 版本异常，只允许关闭             | 禁止                       | 禁止                             |
| 已知维护且空闲                     | 全屏维护待机                     | 禁止                       | 禁止                             |
| 维护期间普通失联                   | 连接异常，保留维护锁             | 禁止                       | 禁止                             |
| 正常模式下临时失联，无已知版本异常 | 连接异常及本地记录入口           | 允许查看、选择导出         | 禁止                             |
| 设备禁用或服务许可无效             | 对应异常                         | 首版不开放                 | 禁止                             |
| ready                              | 试卷列表、处理中/异常/历史       | 允许                       | 允许，仍逐请求准入               |
| 已开始练习遇断网/维护/禁用         | 保持播放器，提示由宿主非阻断展示 | 结束后按最新准入           | 禁止下一场；已完成作答先本地保存 |

收到维护或版本异常时关闭列表操作与未执行确认框；正在进行的本地完整保存不能被页面卸载打断。维护测试只在已激活、同版本、维护且空闲时开始；不得占用活动播放器的麦克风。

## 3. 连接、心跳与响应乱序

本地绑定包含 `serverId`、可信公钥指纹、baseUrl、deviceId、宿主保存的凭证引用、运行代次和最后已知维护/版本事实。设备凭证、运行代次由 main 管理，renderer 不读明文秘密。

应用进程每次启动按 API 原子增加代次并生成 runtime ID；同一主进程的 renderer 重建不创建新运行，序号由 main 单调分配，renderer 不得从 1 重置。首条成功心跳建立服务端当前运行，之后每 5 秒一次；请求串行，控制请求超时初始 10 秒。断线按 1、2、5、10 秒加少量抖动重连，最大 10 秒；明确版本/权限拒绝保留诊断轮询，撤销凭证后停止自动使用它。

每次连接尝试或换绑生成仅本地使用的 `connectionEpoch`，网络结果带回该值。旧 epoch 的页面、模式、设备和任务响应一律忽略；作答成功回执单独按原提交身份处理，不能因切页丢失。新可信连接取得首次状态后重新建立 mode/device revision 基线，以允许服务恢复旧备份后的版本回退；维护锁在这次状态成功前保持。基线建立后，小修订号不能回退同一连接内的模式或设备配置。

学生端缓存完整设备字段用于维护画面。心跳统计从持久队列计算，不能从当前页面的筛选结果计算。所有诊断快照中的时间表示观测时间，不表示收卷完成事实。

心跳或任务请求收到 `503 SERVICE_NOT_READY` 时，renderer 控制器记录服务暂不可用并保留最后已知维护锁，暂停新的远程业务；不清除绑定、运行代次或本地归档，也不打断已经开始的本地练习和保存。按 `Retry-After` 的等待下限加抖动重试状态/心跳；缺失时使用上述重连退避。只读状态成功仍不能视为写入已恢复，领取前须本次运行心跳成功，并重新检查维护、版本、设备和本地空闲状态。UI 只展示控制器推导的状态，不根据备份 kind 自行解锁；无需新增学生状态响应字段或展示服务端备份内部阶段。

## 4. 练习与播放器交接

1. 下载完整试卷，校验归档摘要及资源；缓存键由 server ID、exam ID 和摘要组成。下载中断保留为临时文件，不作为有效缓存。当前播放器持有缓存引用时不得回收。
2. 进入播放器身份和麦克风预检；学生修改姓名学号时尚未产生正式准入。
3. 预检成功后，宿主生成并保存固定 submission ID 与待准入记录，调用开始许可。请求失败不得开始时间线；相同内容可在有效期内复用 ID 重试。过期且未开始则弃用旧准入并分配新 ID。
4. 返回许可后，再检查连接 epoch、版本、模式 revision 及保守剩余有效期；无新限制时立即开始。超时或已知维护则停在预检，不自动在恢复正常后开场。
5. 时间线结束时固定 submittedAt、答案及录音，组包成功后缓存同一份 Blob。调用宿主保存完整归档与提交记录，等待持久成功后显示完成；重试不重新生成 ID、时间或归档。
6. 保存成功后根据最新准入返回列表或维护待机。网络上传独立执行，失败不阻塞下一场准入。

首版不恢复崩溃前未完成的练习；只留下待准入或活动标记、没有完整归档的记录在启动时标为中断，不进入提交统计。完整归档一旦可靠保存，重启必须恢复提交记录，即使播放器尚未收到保存成功响应。

## 5. 本地持久化

沿用现有原子文件与 CAS 能力，采用每条作答一份版本化 JSON 日志与不可变原归档；首版无需在学生端再引入 SQLite。所有写入由 main 单进程串行执行，renderer 通过期望版本更新单条记录。

```text
student-data/
  binding.json
  practices/<submissionId>.json
  submissions/<submissionId>/record.json
  submissions/<submissionId>/archive.lssubmission
  submissions/<submissionId>/save-intent.json
  tasks/<taskId>/journal.json
  cache/<opaqueCacheId>/
```

先持久化 save intent（身份、固定路径、预期摘要和大小），再写临时归档、同步、发布不可变原归档，最后原子写 record。record 完成后才返回本地保存成功。启动时有 intent 且归档完整可验证，则恢复为 queued；归档未完成不伪造已完成作答，保留错误诊断并清理无效临时部分。record 已存在时校验相同 ID、摘要和原服务，不覆盖不同内容。全机目录不得由学校还原软件回滚。

record 保存：schemaVersion、revision、submissionId、原 serverId/deviceId/凭证引用、原 baseUrl 与指纹、examId、学生身份、submittedAt、archiveSha256、archiveBytes、状态、attemptId、attemptCount、resultKnowledge、retryPolicy、pauseReason、lastError、receipt、completedAt。导出需要的列表字段可以从记录读取；清理归档后保留最小身份、摘要与成功回执标记。

`resultKnowledge` 为 `never-sent`、`unknown`、`not-received`、`received`；`retryPolicy` 为 `automatic-first`、`automatic-maintenance`、`manual`、`receipt-only`、`none`。暂停原因是独立字段（维护、离线、版本、禁用、激活等），不能把失败状态改回首次待上传。

## 6. 提交转换表

| 当前状态与事件                                  | 先保存的变化                                                            | 后续动作                                                                           |
| ----------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 本地完整保存成功                                | queued、never-sent、automatic-first                                     | ready 且仍是原绑定时调度首次上传                                                   |
| 取得上传执行权                                  | sending、新 attemptId、次数增加、unknown                                | 持久化成功后才发网络字节；每份作答最多一个活动请求                                 |
| 上传成功或查询 received/deleted                 | 校验身份与摘要，持久化 receipt、completed、none                         | 归入历史，永久停止该逻辑提交的网络调度                                             |
| 发送中收到维护拒绝，或因已知维护主动取消        | checking、unknown、维护暂停；原来不是 manual 时设 automatic-maintenance | 恢复 ready 后先查回执                                                              |
| 发送出现普通网络错误、HTTP 失败                 | checking、unknown、manual、lastError                                    | 进入异常，可在允许时自动核对；不自动再次 PUT                                       |
| 查询 receiving                                  | checking、unknown，保留原重试策略                                       | 按 Retry-After 再查询，禁止同时上传                                                |
| 查询 not-received 且策略 automatic-maintenance  | queued、not-received，保持该策略                                        | 自动重发同一原归档一次；再次普通失败转 manual                                      |
| 查询 not-received 且策略 manual                 | retry-required、not-received                                            | 等待学生手动重试                                                                   |
| 学生点击重试                                    | 保存手动尝试意图，不清除既有 receipt                                    | 先查回执，明确 not-received 后只为本次意图发送一次；意图不跨进程恢复为自动上传资格 |
| 查询失败或被准入拒绝                            | 保持 unknown 与原策略，更新暂停/错误                                    | 等条件恢复再核对，不能推断未收取                                                   |
| NOT_FOUND、内容冲突、包非法等明确需要处理的错误 | manual-resolution，保存原因与原归档                                     | 不循环创建新 ID 或重新组包；允许时人工导出                                         |
| 应用退出时为 sending                            | 启动恢复为 checking、unknown、manual，除非已持久化明确维护暂停          | 先查询；不确定的中止不推断为维护自动重传                                           |
| 换绑后仍未 completed                            | 保留原目标；策略 receipt-only                                           | 只核对原服务或导出，不能上传到原服务或新服务                                       |

重启时已经保存了成功回执则直接 completed；仅回执内存存在、落盘失败时保持原归档与待确认状态，界面不得称“提交完成”。收到晚到有效回执即使目前维护也可本地保存；这是原请求的完成处理。普通错误之后才发现维护，不追溯授予 automatic-maintenance。

重试查询采用有限并发与退避：单记录串行，初始 5 秒、逐步到 60 秒；离线与维护期间不发查询，恢复 ready 后立即核对。同一设备的正式上传串行，查询最多并发 2 个，所有请求接受取消信号；服务返回 429 时按 Retry-After 等待，已经发起过的上传仍先查询结果。

处理中、异常和心跳统计是不同投影：`waitingFirstUpload` 是 never-sent 且原归档存在的记录；`unconfirmed` 是 unknown 的记录；`failed` 是携带普通失败或需人工处理的未完成记录，允许与 unknown 重叠。maintenance 暂停本身不计普通失败。completed 只进入历史。

## 7. 换绑与旧服务核对

入网命令必须通过激活、版本和忙碌检查。正在播放、保存或执行维护任务时拒绝；先取消并等待后台传输收敛、持久化所有状态，再原子替换绑定。切换失败时保留旧绑定，不出现一半新身份一半旧指纹。

旧提交保存原目标信任和必要凭证引用，仅用于回执查询；不参与旧服务心跳或任务领取。当前应用符合正常业务条件且原服务也通过版本、许可、模式和凭证检查时才核对；原服务维护、不可达或凭证撤销时保持未确认并允许按当前准入导出。永不将旧归档改成新服务身份。旧凭证不能通过当前绑定通用 API 被拿来发起上传。

普通同服务、同凭证的幂等入网不改变绑定上下文或队列资格。教师重置凭证后重新绑定，即使服务和设备 ID 相同，也建立新的绑定上下文，旧队列不自动获得上传资格；需要保留的历史及原回执继续展示。收到属于旧连接的有效回执按 submission ID 定位原记录，不写入新连接的页面状态。

## 8. 维护任务、清理与关闭

任务领取前先持久化任务及执行意图；领取响应丢失可用相同 runtime ID 取回有效租约。执行前保存 lease ID、固定参数与截止时间；本地单调计时采用请求发出到收到响应的完整耗时作为保守余量，不直接信任本机墙钟。超期、续租失败或取消时停止新的副作用，释放音频资源。

| 领取/续租响应 | renderer 控制器与宿主动作 |
| --- | --- |
| 领取 409 RESOURCE_BUSY，含 backup-pending/backup-running | 保持维护待机和未执行意图；按 Retry-After 或重连退避刷新状态、心跳及任务列表，任务仍可领取且本地空闲时重试同一 task/runtime |
| 领取 503 SERVICE_NOT_READY | 不视为领取成功、不产生副作用；按第 3 节等待写入恢复。此前领取结果不明时仍用原 task/runtime 确认，避免重复启动 |
| 续租 503、409 或网络失败 | 立即停止新的测试/删除副作用，收敛当前不可中断的文件操作，释放音频并持久化部分结果；不按 Retry-After 延长租约，也不在服务恢复后自动继续旧执行 |
| 非备份的 409、401/403 或版本拒绝 | 按模式、身份、租约或版本规则停止并刷新诊断；撤销凭证停止自动使用，不能无限重试领取 |

已停止任务的不可变结果按原 lease ID 补报；结果接口遇 503 时保留本地日志，按退避重报相同内容，迟到结果由服务端标记 late。正式上传收到 503 仍沿用第 6 节普通 HTTP 失败的 unknown/manual 分支，不能仅凭 Retry-After 自动重传。

清理预览将所有候选的本地 ID、摘要、提交时间与回执摘要排序后，使用规范 JSON 字节计算 selectionDigest，快照可靠落盘后才报告。执行逐项先写删除意图，验证仍有成功回执再删除文件，最后保存结果。删除后但结果落盘前崩溃，依据意图及文件缺失恢复为已删除，不再次累计；无法判断是否由本次删除时记录 alreadyAbsent，不伪造字节数。

应用重启不使用旧租约启动新操作：已完成结果可补报，未完成工作整理部分结果并停止，等待教师新任务处理剩余范围。补报使用原 lease ID 的不可变结果；不能改写已经服务端接收的终态内容。

学生操作系统关闭不受 kiosk 拦截；正常关闭请求按播放器退出确认规则处理，等待正在进行的本地提交日志写入。强杀依本地恢复规则处理。renderer 崩溃不自动继续播放或维护测试，main 取消该 renderer 持有的网络任务并收敛结果，重载后先读取日志。

## 9. 验收

状态转换使用纯逻辑测试覆盖全部表项；文件保存与恢复使用真实临时目录和故障注入；接口 mock 验证错误码与回执分支。Electron 覆盖维护画面、准入失败不启动、保存失败可重试、上传失败可继续下一场、重启恢复、旧响应不改新连接、换绑后只核对旧回执。音频、目标系统断电持久化及学校还原策略另作现场验证。

备份错误专项在后续实现中验证：领取 409/503 不启动执行；心跳 503 后只读状态成功不提前恢复写调度；续租失败停止且恢复后不自动继续；结果补报遇 503 不丢日志；Retry-After 缺失/到期不延长租约；维护锁、本地保存及正式上传的 manual 策略保持。
