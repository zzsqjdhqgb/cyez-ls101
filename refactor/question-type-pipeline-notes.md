# 题目评分管道与 Schema 设计（当前草案）

> 本文整理 2026-08-09 的讨论结论，用于统一题型、Schema、Template 与 Grading Engine 之间的概念边界。
> 当前只整理设计，不要求现有实现立即遵循。

## 一、核心结论

评分管道只区分三种题型：

```text
objective | fixed-reading | freetalk
```

这里的题型描述的是评分所需的数据结构和处理流程，不是考试中的表面名称。

- `objective`：学生提交字符串，Grading Engine 将它与题目提供的“解析”字符串直接比较。
- `fixed-reading`：学生提交一条或多条录音，每条录音都有对应的固定朗读文本。
- `freetalk`：学生提交一条或多条录音，不存在需要逐字对应的固定朗读文本。

“朗读词组”“朗读句子”“朗读短文”都可以使用 `fixed-reading`。“复述”“看图说话”“话题表达”“情景应答”等都可以使用 `freetalk`。这些表面形式的区别由题目内容、Template 流程和评分标准表达，不继续扩展第一层题型枚举。

同一道非客观题可以选择人类评分或 AI 评分：

```text
fixed-reading + human
fixed-reading + ai
freetalk      + human
freetalk      + ai
```

`objective` 不选择 `human` 或 `ai`，当前固定使用字符串直接比较。

## 二、Schema 的职责

Schema 是一个完整的评分单元定义。它负责：

1. 选择 `objective`、`fixed-reading` 或 `freetalk`。
2. 填写该题型自己的评分数据。
3. 定义本评分单元要求的答案格式。
4. 向 Template 暴露需要绑定的题目输入字段及其类型。
5. 规定本评分单元的满分。

Schema 不再有独立的“Schema 配置”或“Schema 配置实例”。评分标准、AI 额外提示词等内容直接属于 Schema 自身的题型数据。

一次 Schema 应用对应一个评分单元，并且只产生一份评分结果。一个评分单元可以消费多个答案。例如，两句朗读句子如果一起评分，Schema 的答案格式包含两个音频项，Grading Engine 聚合两项后只输出一份结果。

## 三、答案格式

Schema 使用一个有序列表定义答案格式。每个列表项只描述一个答案槽位：

```text
AnswerFormatItem
  ├── description
  └── type: string | audio
```

- `description` 说明该答案槽位的语义。
- `type` 说明学生作答的运行期数据类型。
- 列表顺序就是答案顺序，Grading Engine 必须保持该顺序。

例如，两句朗读句子合并评分：

```text
answerFormat:
  - description: 朗读句子第一句
    type: audio
  - description: 朗读句子第二句
    type: audio
```

如果两句需要分别评分，它们应当属于两个评分单元，而不是在同一次 Schema 应用中返回两组分数。

当前三类题型允许的答案格式为：

| 题型 | 答案格式 |
| --- | --- |
| `objective` | 一个 `string` |
| `fixed-reading` | 一个或多个有序的 `audio` |
| `freetalk` | 一个或多个有序的 `audio` |

“响应”是答案格式中的语义槽位，“录音”是 ExamPlayer 产生的运行期资源。Template 负责把答案槽位绑定到实际的选择结果或录音槽位，Schema 不直接依赖 `recordIndex` 等物理索引。

## 四、Schema 暴露给 Template 的输入

除了学生答案，评分还需要静态题目信息。Schema 向 Template 暴露一个字段列表，每个字段都包含名称、说明和类型；Template 必须为本次 Schema 应用完整绑定这些字段。

所有题型默认具有题目描述等公共题目信息。Schema 还可以根据评分需要声明参考答案、评分材料或其他静态字段。题型本身另有以下要求：

### 4.1 `objective`

客观题至少要求：

- 题目描述。
- `解析`，类型为 `string`。
- 一个类型为 `string` 的学生答案。

`解析` 是题目输入，也是当前客观题的直接比较目标。评分时比较学生答案字符串与 `解析` 字符串；相同则得到该评分单元的满分，不同则得到零分。当前不增加标准化、模糊匹配或其他解析规则。

目前没有多选题需求，因此客观题只处理单个字符串答案。以后出现多选题时，可以在客观题的题型数据中增加评分机制，例如少选扣分或直接计零分；当前 Schema 不为这些机制预留字段。

### 4.2 `fixed-reading`

固定朗读题至少要求：

- 题目描述。
- 评分标准。
- 一个或多个音频答案。
- 与每个音频答案按顺序对应的固定朗读文本。
- 评分方式：`human | ai`。
- AI 评分使用的额外提示词，可以为空。

固定朗读文本是题目静态输入，不是学生答案。它用于帮助人类评分者理解题目，并在 AI 评分时传给对应录音的语音纠错系统。

### 4.3 `freetalk`

自由表达题至少要求：

- 题目描述。
- 评分标准。
- 一个或多个音频答案。
- 评分方式：`human | ai`。
- AI 评分使用的额外提示词，可以为空。

`freetalk` 可以使用参考答案、图片说明、情景背景或其他辅助材料，但不存在与录音逐字对应的固定朗读文本。

图片、音频、视频等资源如何通过 Template 字段引用，属于资源传输方式，不改变上述业务结构。

## 五、运行期数据流

推荐的数据流为：

```text
Schema 定义评分单元、题型数据、答案格式和 Template 输入契约
                              ↓
Template 填充静态题目输入，并绑定运行期答案槽位
                              ↓
ExamPlayer 按答案格式产生学生答案
                              ↓
组装 Schema 所需的完整数据
                              ↓
Grading Engine 执行对应评分管道
                              ↓
输出 { score, code }
```

“组装 Schema 所需的完整数据”只是把 Schema 自身数据、Template 题目输入和 ExamPlayer 实际答案放到一起，不引入 Schema 配置、Schema 配置实例或另一套持久化领域模型。

音频在运行时可以表现为文件引用、资源键或可读取的音频对象。这是传输层选择，不改变答案格式中的 `audio` 类型。

## 六、三类评分管道

### 6.1 客观题

```text
学生答案字符串 + 解析字符串
             ↓ 直接比较
        满分或零分
             ↓
      { score, code }
```

客观题当前不调用语音纠错系统、文本 LLM 或人类评分流程。

### 6.2 人类评分

`fixed-reading` 和 `freetalk` 都可以使用人类评分：

```text
题目输入 + 评分标准 + 有序答案列表
                    ↓
               人类评分者
                    ↓
             { score, code }
```

人类评分不要求执行语音纠错，也不要求先把录音转换成文本。评分者需要能够访问当前评分单元的全部题目输入和学生答案。

### 6.3 AI 评分

AI 评分包含逐条语音处理和整体文本评分两个阶段：

```text
每条音频答案 ──→ 语音纠错系统 ──→ 该条答案的自然语言纠错结果
                                             │
题目输入 + 评分标准 + ASR 文本 + 有序纠错结果 + 额外提示词
                                             ↓
                                        文本 LLM
                                             ↓
                                      { score, code }
```

语音纠错结果是 Grading Engine 的内部中间结果，不属于 Schema 输入，也不写回题目数据。

语音处理阶段必须遵守以下规则：

- 每条音频答案单独调用语音纠错系统，不能先合并音频。
- `fixed-reading` 为每条音频同时传入与其对应的固定朗读文本。
- `freetalk` 不向语音纠错系统传入固定朗读文本。
- 每条音频的 ASR 文本和纠错结果必须与答案格式保持相同顺序。
- 文本 LLM 在最后一次性接收整个评分单元的有序结果并完成评分。

ASR 文本可以随运行期音频数据提供，也可以在批改流程中产生；其具体来源不改变评分管道。无论来源如何，语音纠错结果始终只在 Grading Engine 内部产生并传递给后续文本 LLM。

## 七、统一输出

所有题型和评分方式都使用同一个输出结构：

```text
GradingResult
  ├── score
  └── code
```

顶层输出不增加评分维度、纠错明细、ASR 文本、评语或其他字段。语音纠错结果等处理信息只属于 Grading Engine 内部。

本文暂不扩展 `code` 的业务语义，只确认它与 `score` 一起构成 Grading Engine 的固定输出契约。

## 八、概念边界

- Schema 定义一个评分单元如何接收题目数据和学生答案，以及如何评分。
- Template 填充 Schema 暴露的静态字段，并把答案格式绑定到 ExamPlayer 的运行期输出。
- ExamPlayer 只负责执行考试流程并产生字符串或音频答案，不理解人类评分、AI 评分或语音纠错。
- Grading Engine 直接消费组装完成的数据，执行客观题、人类评分或 AI 评分管道。
- Schema 没有独立配置层；运行期组装数据也不形成另一套作者态配置模型。
- 一个评分单元可以包含多个答案，但只产生一份 `{ score, code }`。
